## 二、AI 与算法层

| 技术 | 实际版本 | 在本项目中的作用 |
|---|---|---|
| **YOLOv11**（Ultralytics） | ultralytics 8.3.217 | 服装微痕目标检测。权重 `Final_Model_V6_best.pt`，**冻结不训练** |
| **PyTorch** | 2.1.2+cu118 | YOLOv11 的推理后端 |
| **TorchVision** | 0.16.2+cu118 | 随 PyTorch 安装，Ultralytics 依赖 |
| **CUDA** | 11.8（cuDNN 8700） | GPU 加速，单图推理约 20~100 ms |
| **qwen3-vl-plus** | DashScope API | 多模态语义复核：判断"是不是瑕疵、哪一类、要不要信" |
| **OpenAI 兼容协议** | DashScope compatible-mode | VLM 调用走标准 `chat/completions`，便于换成其他厂商模型 |

### 自研算法（不依赖第三方库）

| 模块 | 文件 | 说明 |
|---|---|---|
| 置信度动态路由 | `backend/app/core/router.py` | 论文核心机制：`C ≥ T` 直接接受，`C < T` 转复核 |
| 局部区域裁剪 | `backend/app/core/cropper.py` | 外扩 30% + 过小放大 + 尺度提示生成 |
| 规则结果融合 | `backend/app/core/fusion.py` | VLM 判瑕疵则保留并做**类别纠错**，否则剔除 |
| Agent 工具注册表 | `backend/app/core/agent_tools.py` | Function Calling 风格工具声明与调度 |
| 推理轨迹编排 | `backend/app/core/pipeline.py` | 五步流水线编排 + 每步耗时/结论记录 |
| 检测框匹配评测 | `backend/scripts/validate_subset.py` | IoU=0.5 贪心匹配，严格/类别无关双口径 P/R/F1 |

> **注意**：项目中**没有使用任何深度学习训练框架来训练模型**。
> YOLOv11 权重是既有的冻结模型，大模型是 API 调用。
> 系统的技术含量在"协同推理编排"，不在模型训练。

### 前端技术选择说明

| 选择 | 理由 |
|---|---|
| 不用 TypeScript | 项目规模适中，纯 JS 编译更快、依赖更少 |
| 不用 UI 库（Element/Ant） | 避免引入上千个组件和样式覆盖麻烦，自己写全局样式：源码 14.3 KB → 构建后 11.6 KB → gzip 3.4 KB |
| 不用状态管理（Pinia/Vuex） | 页面间无复杂共享状态，组件内 `ref` 足够 |
| 不用 axios | `fetch` 原生支持，省一个依赖 |
| 检测框用绝对定位 div 而非 SVG | SVG 非等比缩放会拉伸文字；div + 百分比坐标中文标签始终清晰 |

## 附：启动脚本是怎么来的

### 1. 它是我直接写出来的一个纯文本文件

`start.bat` 和 `start.ps1` **不是任何工具生成的**，也不是"打包"出来的。
它们是普通文本文件，我用写文件的方式逐行写出来的，
和写 `README.md`、写 `pipeline.py` 是同一件事。

### 2. 它和"构建产物"的区别

项目里有几类文件，来源完全不同：

| 文件 | 来源 | 能不能手写 |
|---|---|---|
| `frontend/dist/**` | **`vite build` 生成**，改了源码要重新生成 | 不能 |
| `backend/**/__pycache__/` | **Python 自动生成**的字节码缓存 | 不能 |
| `backend/data/clothinspect.db` | **程序运行时生成** | 不能 |
| `start.bat` / `start.ps1` | **人手写（我写的）** | 能，就是纯文本 |

你之前觉得"没打包所以不能用"，是因为把这两类搞混了 ——
`dist` 那种确实必须由构建工具生成，但**启动脚本恰恰是手写的，不需要任何生成过程**。

### 3. 它实际产生的过程

不是先写脚本再验证，而是反过来：

```text
第 1 步：我手动敲命令，把项目跑起来
         cd backend
         & "E:\Miniconda\envs\label-studio\python.exe" run.py --port 8000

第 2 步：发现还有前置步骤，逐个补上
         npm install / npm run build      （前端要先构建）
         检查 python-multipart 装没装     （少依赖会直接报错）

第 3 步：把这条"能跑通的命令序列"固化成一个脚本
         把 cd 换成 $PSScriptRoot
         把写死的 python 路径换成候选列表 + import 试跑
         把"要不要 npm build"换成判断 dist 存不存在
         → start.ps1

第 4 步：再加一层 cmd 批处理，为了能双击
         → start.bat
```

所以本质是：**把"我验证过能跑通的命令序列"翻译成脚本**。
命令序列是我实测出来的（这也是为什么脚本里判断条件那么具体，
比如用 `import ultralytics, fastapi` 试跑而不是看文件夹存不存在）。

### 4. 双击后到底发生了什么

```text
你双击 start.bat
   │
   ├─ cmd.exe 读 start.bat（纯 ASCII，所以解析不会错位）
   │
   ├─ chcp 65001        把控制台切到 UTF-8，否则中文和 Python 日志乱码
   │
   ├─ where powershell   确认系统有 PowerShell
   │
   └─ powershell -ExecutionPolicy Bypass -File start.ps1
         │                ↑ Bypass 绕过"禁止运行脚本"的默认策略
         │                ↑ -File 指定脚本
         │
         └─ start.ps1（有 UTF-8 BOM，PowerShell 5.1 才能正确读中文）
               │
               ├─ $PSScriptRoot 定位项目根目录（不依赖当前工作目录）
               │
               ├─ 1/4 环境探测：候选路径逐个试 import ultralytics, fastapi
               │
               ├─ 2/4 检查 .env（没有就从 .env.example 复制）+ 找权重
               │
               ├─ 3/4 看 frontend/dist/index.html 在不在
               │        不在 → npm install + npm run build
               │
               └─ 4/4 后台起一个隐藏进程，6 秒后开浏览器
                     然后前台执行 python run.py --port 8000
                            （前台 = 窗口不关，服务就不停）
```

### 5. 那为什么"以前的项目没有"

因为写脚本这一步是人（或 AI）额外做的，**不是项目跑起来就自动有的**。
一个项目从"能跑"到"能双击跑"，中间需要有人：

1. 把散落的命令整理成序列
2. 处理各种边界（路径、环境找不到、依赖没装、dist 不存在）
3. 处理编码问题（就是这次踩的 cmd 解析 + PowerShell 5.1 BOM 两个坑）

这三步没人做，项目就永远停在"要手敲命令"的状态。
**你以前的项目不是"缺打包"，是缺这一步。**

### 6. 一个反直觉的点

双击失败那次，报错是 `'rShell' 不是内部或外部命令` ——
`powershell` 这个词被从中间劈开了。这种问题只有**真的双击**才会暴露，
在 PowerShell 7 里手敲 `.\start.ps1` 永远测不出来
（PS7 默认按 UTF-8 读文件，而双击走的 PS 5.1 默认按 GBK 读）。
所以如果你以后自己写启动脚本，**一定要用双击或 `cmd /c` 实测一遍**。
